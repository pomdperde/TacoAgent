# 节点记忆裁剪 A/B 实验

日期：2026-09-01

## 结论

在固定的长上下文夹具中，按八类节点各构造一次记忆快照：引入节点记忆裁剪后，输入量由 58,820 tokens 降至 7,547 tokens，减少 51,273 tokens（87.17%）。本地记忆构造与紧凑 JSON 序列化的中位耗时之和由 34.7551 ms 降至 22.8190 ms，减少 34.34%。

## 方法

- A 组（裁剪前）：复现引入节点配置之前的统一记忆快照；每个节点均接收同一套工作记忆、历史摘要、NOTEPAD 和最多 6 条外部记忆索引。
- B 组（裁剪后）：调用当前 `build_layered_memory`，由节点配置选择字段、字符预算、历史与索引数量。
- 固定数据：长任务、12 个 todo、8 条验收标准、8 条验证命令、研究记录、10 条 handoff、长历史摘要、长 NOTEPAD，以及 6 条 SQLite 外部记忆索引。
- Tokenizer：`tiktoken cl100k_base`。
- 耗时：每组预热 5 次，正式重复 200 次；统计构造记忆并序列化为紧凑 JSON 的中位数和 P95。
- 两组均只注入外部记忆的轻量索引，不注入长详情，因此实验单独衡量“按节点裁剪”的收益。

## 结果

| 节点 | 裁剪前 tokens | 裁剪后 tokens | 降幅 | 前耗时中位数 (ms) | 后耗时中位数 (ms) | 耗时变化 |
|---|---:|---:|---:|---:|---:|---:|
| single_agent_planner | 7,354 | 838 | 88.60% | 4.5196 | 4.2116 | -6.81% |
| multi_agent_supervisor | 7,354 | 838 | 88.60% | 4.3982 | 4.7013 | +6.89% |
| actor | 7,351 | 911 | 87.61% | 4.3182 | 4.1825 | -3.14% |
| codeAgent | 7,352 | 912 | 87.60% | 4.6368 | 4.1505 | -10.49% |
| verifier | 7,352 | 462 | 93.72% | 4.2069 | 2.1708 | -48.40% |
| searchAgent | 7,352 | 270 | 96.33% | 4.2337 | 0.0245 | -99.42% |
| context_monitor | 7,352 | 324 | 95.59% | 4.2782 | 1.1593 | -72.90% |
| context_compressor | 7,353 | 2,992 | 59.31% | 4.1635 | 2.2185 | -46.72% |

表中“耗时变化”负数表示更快。`multi_agent_supervisor` 的约 0.3 ms 回退属于毫秒级本地测量波动；主要收益来自发送给模型的输入显著缩短，而不是本地 Python 构造时间。

## 解读边界

这是离线、确定性的 prompt-input 微基准，没有调用远端模型。因此它不包含输出 token、模型生成时间、服务排队和网络延迟。八节点合计表示统一对比口径，并不等同于某次真实任务必然访问八个节点各一次。真实单轮成本应根据实际执行轨迹，将各节点调用次数乘以相应输入量，并结合供应商返回的 usage/latency 统计。

## 复现

```bash
python -m evals.run_memory_profile_ab --repeats 200
```

机器可读结果位于 `evals/results/memory_profile_ab_latest.json`。回归测试确保所有节点的固定输入 token 均下降，且总体降幅超过 50%。
